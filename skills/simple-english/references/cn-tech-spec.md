約束等級：「必須」= 正確性約束；「應」= 預設採用、允許依據語境調整；「可以」= 可選方式。本規範中所有「必須」即對應 C## 編號本身。

## 3. 正確性與詞語

### C01 必須保留事實和邏輯邊界

保留物件、數量、單位、範圍、條件、否定、例外、預設值和時限。不得把「最多」改成「恰好」、「大於」改成「大於等於」、「通常」改成「總是」、「檢查完成」改成「檢查透過」。可以改變順序和句法，不能改變成立條件。

例：「檢查完成後可以啟動裝置」可改成「完成檢查後，可以啟動裝置」；不能改成「檢查透過後，啟動裝置」，後者新增透過條件，並把許可寫成命令。

### C02 必須區分事實、推斷和未知

確認的事實直接陳述；影響判斷的推斷說明不確定性及依據；未知指出具體缺項。不對每句機械加標籤。

例：「升級後出現故障。原因尚未確認」不能改成「升級導致故障」。

### C03 不得為了通順補造資訊

不得補造地址、命令、路徑、錯誤碼、預期結果、效能數字、恢復方法或因果機制。自擬例子必須標為假設，不能當作操作依據。阻礙執行的缺項寫「待確認：……」；停止給出依賴該缺項的步驟。

### C04 一個概念應使用一個首選術語

固定關鍵物件、動作和狀態的稱呼，不為避免重複輪換同義詞。不同概念不強行合併。術語來自專案上下文或可靠定義。

例：「請求」是一次呼叫，「任務」是呼叫建立的處理物件，兩者不能交替指代同一物件。

### C05 必須按語境判斷詞義

「掛起」「釋放」「關閉」等須結合物件解釋。詞表只能約束明確語境中的對映，不能無條件全域性替換。存在歧義時，寫出完整動作和物件。

### C06 應保留並解釋必要專業術語

準確術語沒有合適日常替代詞時保留，並在讀者需要時解釋。縮寫首次出現時給出必要全稱或解釋，後續一致。不為通俗把「冪等」改成「永遠不會出錯」。機器識別符號和實際 UI 標籤保持原樣。

## 4. 句子與關係

### C07 執行者、動作和物件必須可確定

有歧義時補明主語和賓語，區分人工、系統和第三方行為。上下文唯一時允許中文自然省略。執行者或原因未知時保留未知，不強行改主動句。

例：「選擇『儲存』。系統隨後重新載入配置」，不要寫成兩個使用者操作步驟。

### C08 一句應表達一個主要關係

拆開糾纏的動作、原因和結果；保留必要連線。不設中文固定字數上限，句長僅作複查線索。不能把同步動作拆成先後步驟，也不能拆散條件與被約束動作。

### C09 必須寫清邏輯關係

有證據時明確因果，僅有先後時只表達先後。保持「且/或」「僅當/如果」「即使/除非」的區別。不能把「如果 A，則 B」改成「只有 A，才 B」。條件不清時不擅自選擇解釋。

### C10 必須明確否定範圍和指代

「不支援自動刪除日誌」不能改成「不支援刪除日誌」。允許「其、該、這、上述」，但須能準一定位。多種解釋都成立時指出歧義，要求核實，不猜測。

### C11 應拆開難解析的長定語

多個「的」或名詞堆疊時，寫明物件關係。官方名稱保留並解釋，不自行改名。

例：「使用者任務狀態同步失敗恢復策略」可能指狀態同步失敗，也可能指狀態為「同步失敗」。先核實，再改寫。

### C12 應用直接、具體的動作詞

「進行配置調整」可寫成「修改配置」；「處理異常」須說明是記錄、重試、停止還是上報。刪無資訊修飾和黑話，但不刪除準確術語、真實能力及必要限定。

## 5. 概念解釋與方案說明

### C13 應從讀者問題逐步展開

先回答，再解釋必要機制，隨後給例子和邊界。新概念首次使用處解釋。不堆定義，不強制每次包含所有欄目。

### C14 每段應有一個主要主題

自然段講機制和因果；編號講先後步驟；列表講並列項；表格講比較。不要把所有句子拆成列表，也不要把有序步驟寫成一段散文。簡短答案可以只有一段。

### C15 類比必須說明適用邊界

類比幫助建立直覺，不能代替機制或證明。重要區別應說明。數值例子須與資料一致；自擬例子標為假設。

### C16 程式碼和方案說明必須區分改變與證據

按需要交代問題、具體改變、輸入輸出、依賴、失敗行為與驗證結果。只報告做過的驗證。不把「增加檢查」寫成「徹底解決」，不從實現意圖推斷安全或效能收益。

## 6. 操作說明

### C17 必要條件和風險必須先於動作

執行前必須知道的條件放在動作前；多項前提可以集中列出。只約束某一步的條件放在該步前。不藏在末尾括號、腳註或可跳過的備註中。

### C18 一步應包含一個主要操作

按實際執行順序編寫。必須同時發生的動作保留同一步，明確「同時」。系統行為作為結果說明，不偽裝成人工步驟。不得補造缺失引數。

### C19 應提供可觀察的判斷條件

資料支援時說明成功、失敗和停止標誌；未知時指出缺少驗證依據，不把預期當作已驗證結果。恢復方法必須有來源及適用條件。

### C20 風險提示必須給出具體風險

實際風險與當前動作相關時，說明禁止或必要動作，以及可能後果。風險等級採用行業或專案定義，不把某個領域的風險標籤直接當作所有領域的強制分類。風險等級未知時，直接陳述具體動作及可能後果，不自行評級。無依據不新增泛化警告。

## 7. 故障排查

### C21 必須區分現象、假設、檢查和結論

從觀察與證據出發。假設說明為何值得檢查；檢查說明觀察什麼，以及不同結果的意義。僅支援部分結論時不能宣稱定位根因。

### C22 應優先做有證據價值且風險低的檢查

技術依賴允許時先讀狀態和日誌，再考慮改變系統。無證據時不先刪除資料或關閉保護。這是排障說明的預設安排；技術依賴需要其他順序時，說明理由。

## 8. 格式與交付

### C23 必須保護機器可讀內容

程式碼、命令、路徑、URL、JSON 鍵、API 識別符號、變數、錯誤碼不能為簡化語言而修改。明確要求修正程式碼時才按技術規則修改。原文引用與改寫分開，不把改寫偽裝成原話。

### C24 必須複查語義與任務可用性

核對條件、範圍、數字、否定、術語和確定程度。讀者應能定位資訊、理解邊界、執行或判斷下一步。資料缺失影響目標時具體指出；無需展示全部內部檢查過程。

## 9. 術語約定（建議，不是封閉中文詞典）

| 詞語 | 約定 | 不等於 |
|---|---|---|
| 必須 | 必要要求 | 推薦 |
| 建議 | 預設推薦 | 必須 |
| 允許 | 許可 | 能力或命令 |
| 能夠 | 能力 | 獲得許可 |
| 可能 | 不確定性 | 一定 |
| 通常 | 常見情況 | 所有情況 |
| 已驗證 | 已執行且有結果的檢查 | 理論上應有效 |
| 待確認 | 資料不足須核實 | 預設合理猜測 |

「可以」能表達許可、能力或可能性，不一律禁止；區別影響判斷時改用明確措辭。

## 23. 失敗模式與修正

| 失敗模式 | 修正方法 |
|---|---|
| 過度簡化 | 恢復必要資訊，改句法而不改事實 |
| 過度列點 | 有關聯資訊寫段落，補連線詞，保留真正並列項 |
| 假精確 | 區分規範要求、專案約定和作者建議；中文句長沒有從英文詞數自動推導的法定上限 |
| 假完整 | 具體標明缺項並停止依賴它的操作說明 |
| 假定（推測當事實） | 恢復確定程度並說明可觀察證據 |
| 機械術語替換 | 按概念處理，先核實詞義；批次替換後逐項複查機器內容與引用 |
